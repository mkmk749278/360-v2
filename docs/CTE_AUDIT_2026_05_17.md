## TL;DR (one page)

**What's good**
- Engine doctrine ("HTF Structure, LTF Entry") is genuinely enforced in the 6 signal-producing paths we touched in Stream C — not just written in docs, but wired in code.
- Pre-TP partial-close mechanic is mainstream in credible crypto-trading practice (Linda Raschke, Al Brooks, Mark Douglas all teach scale-out-then-breakeven). The −0.5% vs −7.9% asymmetry argument holds.
- Capital-preservation loop is wired end-to-end now: engine fires pre-TP → app sees `preTpHit` → user's Binance account closes the partial. Three layers of idempotency.
- The ops dashboard at `ops.luminapp.org` is **live and running** with 32 tests passing. (Our own internal docs were stale on this — said "not started.")

**What's weak**
- The mobile app has **zero unit tests**. 43 Dart files, all production code, validated by visual review only. Idempotency, partial-close split, and passive-protect state machine are unverified.
- Our signal volume (286 in 20 hours) is **3× the upper bound for credible signal channels**. Industry-credible ranges: 1–5/day quality, 5–10/day yellow flag, 10+/day low-quality marketing.
- Default leverage is 10× with 5–60 min holds. Credible scalping desks quote 3–5× for this hold profile, especially with funding events that can straddle the position.
- Engine-side per-user `grab_fraction` and invalidation mode are stored in the database but **not consumed by the engine yet** — Phase 4 deferral, known, but a future refactor liability.

**Biggest risk**
- **Tight invalidation mode stacks four kill conditions** (ATR-MFE retrace, regime shift, EMA cross, momentum threshold). Credible literature (Perry Kaufman, Van Tharp) is clear: each additional kill rule must earn its keep with an ablation showing incremental contribution. We've never run that ablation. There's a real chance one or more of these is silently cutting winners with no offsetting protection.

**One thing to do this week**
Run an ablation on Tight invalidation mode using the historical cohort. If any kill rule's removal does not measurably worsen the MFE-give-back metric, drop it. This is the single highest-leverage forensic action available.

## Part 1 — How We Compare to Credible Industry Practice

### 1.1 — The honest landscape

There is no "institutional crypto signal Telegram desk." The institutional layer (QCP Capital, Wintermute, Cumberland DRW, GSR, B2C2, FalconX, Jump Crypto) publishes **research and flow color**, not discrete entry/SL/TP signals. Anyone marketing themselves as institutional-grade signals is in the retail-prosumer tier.

Our actual competitive set is that retail-prosumer tier: Fat Pig Signals, MyCryptoParadise, Crypto Inner Circle, Evening Trader, Signals Blue. **All of them claim 90%+ win rates. An independent audit of 549 signals across this tier returned a composite 70.5%.** The FTC and FCA both flag 95%+ win-rate claims as fraud markers.

Implication for us: when we ship public win-rate numbers (we don't yet), the bar that proves credibility is **70–80% measured on a published cohort with the methodology fully open**. Any claim above 85% will be assumed to be marketing.

We are not doing anything fundamentally weird, but we are dialed several notches hotter than the credible practitioner consensus.

## Part 2 — Doctrine Validation: Pre-TP & Invalidation

### 2.1 — Pre-TP partial close: **mainstream, well-aligned**

Partial-close-then-breakeven is the most widely-taught discretionary trade-management pattern in post-2000 trading literature.

| Source | What they teach | Match with us |
|---|---|---|
| **Linda Raschke** (Street Smarts, Market Wizards) | "I'm always scaling out of trades" + move stop to BE | ✓ Identical doctrine |
| **Al Brooks** (Reading Price Charts) | "Take profit on part, swing part" — the middle path | ✓ Identical |
| **Mark Douglas** (Trading in the Zone) | 33/33/33 scale at 1R / 2R / runner with BE ratchet | ✓ Similar shape, different fractions |
| **Van Tharp / Howard Bandy** | "Scale-out without an additional valid signal reduces expectancy" | ⚠ Counter-argument we should know |
| **Tom Hougaard** | Critic — argues for *adding* to winners | ⚠ Minority view |

**Where the math agrees with us:** The full-SL asymmetry argument (−7.9% vs −0.5%) is a legitimate articulation of what the literature calls the "BE-ratchet leg" — an asymmetric reward addition that pure expectancy math ignores.

**Where the math disagrees with us:** Bandy's simulation work (4,176 trades, 72 instruments) shows plain scale-out without a confirming signal reduces expectancy. The reconciliation is that the BE-ratchet — which we have — restores the asymmetric reward leg. So our doctrine is on the defensible side of the literature debate, **provided the BE ratchet is actually firing reliably**.

**Two soft flags:**

1. **Anchor coupling.** Our pre-TP threshold is "fraction of path to TP1" (e.g. 30–60% of the way). The standard literature uses R-multiples (close ½ at 1R). Both work, but our framing **ties our pre-TP trigger to our TP1 placement** — if TP1 drifts because of regime, ATR, or path-specific geometry, our pre-TP drifts with it. R-multiple anchors don't have this coupling. This is either a feature (path-adaptive) or a bug (one knob's drift contaminates another), depending on whether both TP1 and the pre-TP threshold come from the same volatility estimator.

2. **Range too wide.** B17 allows users to configure `grab_fraction` from 30% to 100%. The literature consensus zone is 33–50%. **At 100%, the user has disabled their runner entirely** — which is the worst-of-both-worlds case Van Tharp explicitly warns about (selling your highest-EV inventory cheapest with nothing left to ride). Recommendation: tighten UI range to 40–60%, keep DB range at 30–100% for forensic.

### 2.2 — Invalidation modes: **concept mainstream, Tight is over-engineered**

| Source | What they teach | Match with us |
|---|---|---|
| **Linda Raschke / Al Brooks** | Thesis-broken early exit on shorter timeframes | ✓ Our timeframe regime |
| **Ed Seykota / Larry Hite** (trend-followers) | Stop *is* the invalidation; early exit truncates fat tails | ✗ But they trade higher TF |
| **John Sweeney** (MFE methodology, 1990s) | MFE-anchored exits | ✓ Lineage for our ATR-MFE-retrace |
| **Chuck LeBeau** (Chandelier Exit) | Hang stop N×ATR off MFE peak | ✓ Direct ancestor of our mechanic |
| **Van Tharp / Howard Bandy** | MFE-anchored exits valid; classify each rule's contribution | ✓ Validates the concept |
| **Perry Kaufman** (Trading Systems and Methods, 6e) | "Each additional exit rule must earn its keep — otherwise it just cuts winners short" | ✗ **The bar we may be failing** |

**What's mainstream:** thesis-broken early exit on 5m / 5-60min holds (our regime); MFE-anchored ATR-trailing stops (our mechanic); preset modes like Tight/Standard/Loose (normal product design).

**What's specifically novel-but-principled:** our percentage-retracement-of-MFE rule ("close at 50% retracement of MFE peak") is closer to a "give-back stop" from CTA practice (Curtis Faith, "Way of the Turtle" appendix) than a classic ATR-multiple Chandelier. Defensible, less battle-tested.

**The real risk:** Tight mode currently runs **four independent kill conditions in parallel**:

1. ATR-MFE retrace (50% give-back when MFE ≥ 0.3R)
2. Regime-shift kill
3. EMA crossover kill
4. Momentum-threshold kill

The Kaufman-test verdict: each rule must independently improve the MFE-give-back vs. truncated-winner tradeoff. We have not run this ablation. **At least one of these rules is almost certainly redundant** (riding along on the same signal as another), and possibly bleeding away winners with no offsetting protection.

**Recommended action:** ablation table. Re-run the historical cohort with each Tight kill rule disabled in turn. Drop any whose removal doesn't worsen MFE-give-back by a measurable amount. This is the single highest-leverage doctrine action available.

**Pre-TP and invalidation mechanics**

`_check_pre_tp_grab` correctly fires a real broker partial close via `close_partial(sig, grab_fraction, tp_level=0)`. Idempotent on `(signal_id, tp_level)`. Fee-aware math: gross × leverage − round-trip-fee × leverage. Residual SL ratcheted to entry, never widens. **Correct.**

`_check_invalidation` implements three modes (loose/standard/tight). Tight adds ATR-trailing kill at MFE ≥ 0.3R, 50% retrace. **MFE protection rule** (when pre-TP fired and price still favourable, skip all kill checks) — solid. Regime-flip gate uses change-from-creation-regime, not match-killer-regime. **Correct.**

**Scoring engine**

Multi-component (risk, trend, liquidity, spread, data, order-flow). All gradient-based, no clipping. Confidence tiers: A+ ≥80, B 65–79, FILTERED <65. Risk component recalibrated 2026-04-30 against truth-report data.

Gamability check: no single feature can lift sub-50 to paid-65. Confluence bonus capped. Order-flow CVD contribution capped at 500k USD. **Evidence-grounded.**

**Telemetry**

Truth report captures per-path, per-score, per-pair, per-pair-tier P&L honestly. Invalidation audit classifies kills as PROTECTIVE / PREMATURE / NEUTRAL based on post-kill price action. Per-pair attribution does not hide losers (SIRENUSDT shown at 100% MFE=0, blacklist applied transparently). **No flattening observed.**

**Async hygiene**

Scanner loop bounded by semaphore. No blocking calls. Queue bounded at 500 with overflow telemetry every 10th drop. `_check_invalidation` is synchronous (intentional — no I/O, just math). **Clean.**

**Per-user settings consumption (THE LIABILITY)**

`user_pretp_settings.grab_fraction` and `user_invalidation_settings.mode` exist in the schema. They are **NOT** read by the engine yet:

- `_check_pre_tp_grab` line 1722 hardcodes `grab_fraction = float(PRE_TP_GRAB_FRACTION)` (the engine default).
- `_check_invalidation` uses `INVALIDATION_MODE_DEFAULT`.

This is **architecturally correct today**: engine TradeMonitor runs the owner's paper broker, one config, one set of values. Per-user execution happens on the app side (PR #28 + #29) where the user's actual Binance account receives the partial close.

**When this becomes a bug:** if we ever move per-user auto-trade to a server-side broker integration (instead of the user's own Binance keys), the engine must read `user_overrides.get_pretp(user_id).grab_fraction` per signal. The schema is ready; the wiring isn't.

**Vendor-API resilience**

WS path migration (2026-04-23) was fixed in PR #394. The fallback logic in `websocket_manager.py` still tries deprecated `/ws`, `/stream`, `/market/ws` paths after the primary `/market/stream`. Defensible (defence in depth), but a hard rejection from Binance in future would mean silent fallback failure. Recommendation: add an env flag `REQUIRE_MARKET_STREAM_PATH=true` for staging, log deprecation warnings when fallback succeeds.

**Minor surface fix**

The 9 exempt evaluators (tape-driven + breakout + PDC + CLS) have no in-code docstring marker explaining why they don't consume HTF infrastructure. Reader of the architecture map opens scalp.py and sees WHALE/VSB/BDS with no LevelBook usage — creates surface confusion. Low-effort fix: `# EXEMPT FROM HTF_DOCTRINE (tape-driven)` above each.

### 3.2 — `lumin-app` (mobile) — **Capital preservation solid; zero test coverage**

**Capital-preservation wiring**

User's `grab_fraction` reaches the user's Binance account at pre-TP time. Trace verified:

```
PretpSettings.grabFraction
    → fetchUserPretpSettings (AutoTradeWatcher._firePreTp)
    → grabFraction clamped [0.30, 1.00]
    → OrderExecutor.executePreTpPartial
    → BinanceClient.closePartialMarket (reduceOnly=true, deterministic clientOrderId)
```

Three idempotency layers confirmed:

1. **Local** — caller checks `existing.preTpBanked` before invoking.
2. **Broker** — `lumin-pretp-{signalId}` and `lumin-be-{signalId}` clientOrderIds reject Binance-side duplicates.
3. **Log overwrite** — successful fire writes `preTpClosedAt`, next tick short-circuits at layer 1.

**Manual-entry coverage (post PR #29)**

Passive-protect mode logic verified: `mode == 'off' AND protectManualEntries == true AND keys present` → watcher polls, runs pass 2 only (pre-TP partials), pass 1 (new entries) is skipped. AUTO banner shows "AUTO PROTECT". Kill switch in protect mode flips `protect_manual_entries` to false (not `mode`, which is already off).

No dead zone identified.

**Idempotency asymmetry (THE RISK)**

Pre-TP partial-close splits the SL relocation into two broker calls:

1. Place reduce-only MARKET close for `grab_fraction × entry_qty`
2. Cancel original SL
3. Place new STOP_MARKET at entry price (breakeven, closePosition=true)

**If step 1 succeeds but step 3 fails**, the partial is banked but the residual position has **no SL at all** until the user notices. The order log records this state correctly, the UX surfaces a warning ("Residual still open; place BE SL on Binance"), but there is no retry — the next tick sees `existing.preTpBanked == true` and skips. Manual recovery only.

**No retry on transient Binance failures (the other risk)**

`_signedPost` has no retry loop. A 429 (rate limit) or 5xx during order placement fails immediately. Order log surfaces the error but no exponential backoff. Acceptable for Phase 3b-2 (manual fallback available), gap for Phase 4 claimed autonomy.

**App-only autonomy**

`AutoTradeWatcher` stops when the app backgrounds. Honest UX (the AUTO banner says so), but it caps the value proposition for true 24/7 trading. Foreground service is a known Phase 3.5 item.

**Settings page honesty**

Pre-TP settings page: accurately describes scope (per-user, applies via your Binance keys). Invalidation settings page copy is slightly stale — still says "consumed by the app-side OrderExecutor in Phase 4," which is now Phase 4 = today for the partial-close path. Should be updated.

**Test coverage (THE GAP)**

**Zero test files. No `test/` directory.** 43 Dart files validated by visual review only.

Highest-value tests to add, in priority order:

1. `test/data/auto_trade_watcher_test.dart` — passive-protect state transitions, pass 1 vs pass 2 branching, kill switch routing.
2. `test/data/order_executor_test.dart` — partial-close idempotency, cancel-then-replace failure modes, grab_fraction clamping.
3. `test/data/order_log_test.dart` — entry creation, duplicate detection, pruning, JSON serialisation.
4. `test/data/binance_client_test.dart` — HMAC signing, query construction, filter rounding.
5. `test/features/settings/pretp_settings_page_test.dart` — load/save cycle, slider bounds, protect switch.

This is the single largest engineering-hygiene gap in the entire stack. Idempotency regression on a user's live Binance account could mean double-fires on real money.
